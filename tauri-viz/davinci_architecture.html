Davinci 核心概览

Davinci 是一款单线程、4 宽、乱序处理器核，面向 AI 推理、HPC 和密集线性代数工作负载设计。 它执行统一的指令流，包含四个指令域——标量 (Scalar)、向量 (Vector)、 矩阵 (Cube) 和 内存 Tile 引擎 (MTE)——共享流水线前端，分布式后端执行单元。 该核不支持精确中断或异常，仅执行 run-to-completion 内核，从而消除了重排序缓冲区 (ROB) 和顺序退休， 产生更简单、更低功耗的 OoO 引擎，等价于 Tomasulo 原始算法（IBM 360/91, 1967）。

关键设计决策

64-bit RISC 标量 ISA

类似 ARM / RISC-V 风格的指令集，提供通用控制流和地址计算。

Cube ISA — 外积累积

Tile 级外积累积指令驱动 outerCube MXU，硬件管理 K 循环。

统一 Tile 寄存器架构

TRegFile-4K (1MB, 8R+8W) 作为向量、矩阵和 MTE 的统一物理寄存器。无独立 VRF。

无 ROB — 回归 Tomasulo 原始算法

参考计数释放物理寄存器，无需顺序退休。RAT + Checkpoint 分支恢复。

Davinci 核心架构总览

上图展示了 Davinci 处理器的整体微架构，由四大子系统组成：

  • 前端 (Front-End)：包含分支预测器（TAGE + BTB + RAS）、取指单元（4-wide, L1-I）、指令缓冲区（16 entries）和译码+重命名（4-wide）。双 RAT 分别映射标量寄存器（32→128）和 Tile 寄存器（32→256），通过 8-slot checkpoint 支持分支恢复。
  • 派发与执行：重命名后微操作按域路由到 5 个保留站（Scalar 32 / LSU 24 / Vector 16 / Cube 4 / MTE 16），每个 RS 独立发射。执行单元包含 6 个标量端口、LSU、512b 向量单元和 4096-MAC outerCube 矩阵单元。
  • 结果广播：CDB（6 端口）广播标量结果（7-bit tag + 64-bit data），TCB（4 端口）广播 Tile 完成信号（仅 8-bit tag，无 data payload，因为 Tile 数据直接写入 TRegFile）。
  • 寄存器堆与存储：标量物理 RF（128×64b）和 TRegFile-4K（256×4KB=1MB）分离。三级 cache（L1-I 64KB / L1-D 64KB / L2 512KB）层次通过 NoC 连接外部存储。

流水线与微架构

Davinci 核心采用 12 级标量流水线，无 retire 阶段。所有指令域共享前端（F1–D2）， 在派发（DS）阶段路由到域特定保留站，乱序发射（IS）和执行（EX1–EXn）。

前端：取指与分支预测

取指单元

  • 取指宽度：4 instructions / cycle (16 bytes)
  • 对齐方式：16-byte aligned fetch block
  • 指令缓冲区：16 entries（4 周期解耦）
  • L1-I cache：64 KB, 4-way, 64 B line, 2-cycle latency
  • I-TLB：64 entries, fully associative

Fetch 重定向优先级

  1. 分支误预测（EX1 触发）— flush + restart
  2. BTB/TAGE taken（F2 触发）— 下一周期重定向
  3. 顺序 PC+16（默认）

BTB 与 RAS

Branch Target Buffer (BTB)

  • Entries: 2048
  • Associativity: 4-way set-associative
  • Tag: partial PC (upper bits)
  • Target: full 64-bit target address
  • Hit latency: 1 cycle (end of F1)

Return Address Stack (RAS)

  • Depth: 16 entries
  • Push on JAL/JALR to link register
  • Pop on JALR from link register (return pattern)
  • Speculative: checkpoint RAS top-of-stack with RAT checkpoints

译码 (D1)

D1 每周期译码 4 条指令，识别域、opcode、源/目标寄存器和立即数。

  • 译码宽度：4 instructions / cycle
  • 域分类：Opcode[6:5] → scalar / vector / cube / MTE
  • 立即数提取：符号扩展和格式相关提取
  • 分支检测：识别分支指令以分配 checkpoint
  • 无法表达为单微操作的指令在 D1 被拆分为 2 个微操作，消耗 2 个派发槽

重命名 (D2)

重命名阶段使用两个独立的 RAT（Register Alias Table）进行寄存器重命名。 Scalar RAT 映射 32 个架构 GPR 到 128 个物理 GPR，Tile RAT 映射 32 个架构 tile 寄存器到 256 个物理 tile。

Scalar RAT

  • 架构寄存器：32 (X0–X31)
  • 物理寄存器：128 (P0–P127)
  • RAT 存储：32 entries × 7 bits = 224 bits
  • 读端口：8 (2 sources × 4 slots)
  • 写端口：4 (1 dest × 4 slots)

Tile RAT (Vector/Cube/MTE)

  • 架构 tile 寄存器：32 (T0–T31)
  • 物理 tile 寄存器：256 (PT0–PT255), 4 KB each
  • RAT 存储：32 entries × 8 bits = 256 bits
  • 读端口：8 (up to 3 src tiles × 4 slots)
  • 写端口：4 (1 dst tile × 4 slots)

组内旁路逻辑 (Intra-Group Bypass)

当 4 条指令同时重命名时，后条指令可能依赖前条。硬件优先编码比较器检测这些组内依赖：

  • Scalar: 4 slots × 2 sources × 3 older slots = 24 个比较器 (7-bit) + 8 bypass MUX
  • Tile: 4 slots × 3 tile sources × 3 older slots = 36 个比较器 (8-bit) + 12 bypass MUX

双 RAT 重命名流程

D2 阶段每周期重命名 4 条指令，同时维护两个独立的 RAT（Register Alias Table）和对应的 Free List。

  • 源操作数解析：读 RAT 获取源操作数的物理寄存器 tag，同时检查 CDB/TCB 上的广播结果。如果源就绪，直接获取 data；否则仅携带 tag 进入 RS 等待唤醒。
  • 目标寄存器分配：从对应 Free List 出队一个空闲物理寄存器，更新 RAT 映射。旧物理寄存器的 ref-count +1（表示仍有读者），新物理寄存器的 ready bit 设为 0。
  • 组内旁路：4 条同组指令中，后条可能依赖前条的输出。24 个 7-bit 标量比较器 + 36 个 8-bit Tile 比较器实时检测这些组内依赖，直接旁路 tag。
  • 分支 Checkpoint：遇到分支指令时，将双 RAT 状态 + 双 Free List 头指针 + RAS 栈顶打包保存（~499 bits），支持 8 个在飞未解析分支。Flash-copy / flash-restore 均仅需 1 cycle。

Checkpoint 存储 (分支恢复)

  • Checkpoint 槽位：8（支持 8 个在飞未解析分支）
  • Checkpoint 大小：Scalar RAT (224b) + Tile RAT (256b) + scalar free-list head (7b) + tile free-list head (8b) + RAS pointer (4b) = ~499 bits
  • Flash-copy 延迟：1 cycle（双 RAT 并行位拷贝）
  • Flash-restore 延迟：1 cycle（双 RAT 并行恢复）

派发 (DS)

重命名后，每条微操作根据域和操作类型派发到相应保留站。派发有序，发射乱序。

保留站服务条目发射宽度

RS 容量设计原则：RS entries ≈ dispatch rate × average occupancy time。
Scalar RS (32): ~3 dispatch/cy × ~8 cy avg occupancy (ALU 1cy + MUL 4cy + DIV 12-20cy)
Cube RS (4): CUBE.OPA 极长延迟 (N+18 cy) 但极不频繁，每个 GEMM kernel 仅 ~1 条
MTE RS (16): 支持 32-entry outstanding buffer 的 MLP (memory-level parallelism)

发射 (IS)

每个功能单元每周期从其 RS 中选择最老的就绪指令：

  • 选择优先级：age 值最低的 (valid && rdy1 && rdy2) 条目
  • Scalar RS → 最多 4 ALU + 1 MUL + 1 BRU
  • LSU RS → 1 load + 1 store
  • Vector RS → 1 vector op
  • Cube RS → 1 cube op
  • MTE RS → 2 tile ops

CDB 与 TCB

Common Data Bus (CDB)

  • 端口数：6 (4 ALU + 1 MUL/LSU + 1 TILE.GET)
  • 广播宽度：7-bit tag + 64-bit data
  • Snoop: 92 RS entries × 2 scalar sources
  • 用途：标量执行结果广播、唤醒 RS 条目

Tile Completion Bus (TCB)

  • 端口数：4
  • 广播宽度：8-bit tile tag only (无 data payload)
  • TCB0: Vector unit
  • TCB1: Cube unit (CUBE.DRAIN)
  • TCB2-3: MTE unit (TILE.LD/GATHER/ZERO/COPY/PUT)

分支误预测恢复流程

Davinci 的分支恢复机制利用双 RAT 的 checkpoint/restore 设计，在 1 cycle 内完成状态回滚，总惩罚为 6 cycles（对比业界典型的 12-15 cycles）。

  • Cycle c：分支指令在 EX1 阶段解析为误预测。触发 flush 信号，清除 F1 到 IS 所有更年轻的指令。
  • Cycle c+1：Flash-restore 双 RAT checkpoint。双 RAT（Scalar 224b + Tile 256b）和双 Free List head 并行恢复，仅需 1 cycle。同时释放被 flush 指令占用的物理寄存器（ref-count 递减）。
  • Cycle c+2：重定向取指到正确目标地址，TAGE 分支预测器更新历史记录。
  • Cycle c+3 到 c+7：流水线重新填充（F1→F2→D1→D2→DS→IS），共 5 级前端 + 1 级发射。
  • Cycle c+8：第一条正确指令到达 EX1 执行，恢复正常流水线吞吐。

存储与数据通路

Davinci 核心的存储子系统包含 TRegFile-4K（统一 tile 物理寄存器）、三级 cache 层次、 TLB、Store Buffer、以及 MTE（Memory Tile Engine）直连 L2 的 tile 数据通路。

TRegFile-4K 统一 Tile 寄存器堆详解

TRegFile-4K 是 Davinci 架构的核心创新之一，所有 Tile 数据（向量、矩阵、MTE 搬运）统一存储在 1MB SRAM 中，消除了传统架构中 VRF/CRF 之间的数据搬运开销。

  • 存储组织：256 个物理 Tile（每个 4KB）分布在 64 个 SRAM bank 中，每个 bank 深度 256、宽度 512-bit。64 个 bank 分为 8 个 bank-group（每组 8 个 bank），支持 1R+1W 同时访问。
  • Epoch Calendar 轮转：8 个读端口和 8 个写端口通过 8 周期轮转日历访问 bank-group。在 cycle c，端口 p 访问 group (p + c) mod 8。每 8 个 cycle 完成一个 epoch，每个端口恰好读取/写入一个完整 Tile（8 groups × 512B = 4KB）。
  • 端口分配：Cube 活跃时占用 R0-R4（读 A/B 操作数）和 W0（写回 C），剩余 R5-R7 和 W1-W7 供 Vector/MTE 使用。Cube 空闲时全部 16 端口可用。
  • 零气泡链接：连续 epoch 可以背靠背执行（zero-bubble epoch chaining），例如 Vector 2-epoch 操作占用连续 16 cycles。

VEC-4K 向量数据通路详解

VEC-4K 是 Davinci 的向量执行单元，处理 512b 宽度的元素级操作。它采用 strip-based 处理模型，将一个 4KB Tile 分为 8 个 strip（每个 512B）进行逐 strip 计算。

  • 128 独立计算组：每个 Tile 的 8 strips × 64 elements / strip 被分配到 128 个独立计算组。这允许细粒度的数据并行和 fault tolerance。
  • 操作类型：VADD/VMUL（2 源，1 epoch 读 + 1 epoch 写 = 16 cycles）、VFMA（3 源，同样 16 cycles）、VROWSUM/VCOLSUM（跨 strip reduce，16 cycles 但非流水线）、VEXPAND（基于 Fiber ID 的广播扩展）。
  • Fiber ID：每个计算组携带一个 Fiber ID，用于 reduce（跨 group 汇总）和 expand（从一个元素广播到整个 strip）操作。这是 VEC-4K 支持灵活数据布局的关键机制。
  • 延迟：2 epochs（8R + 8W）= 16 cycles 端到端。双源操作和三源 FMA 的延迟相同，因为瓶颈在 TRegFile 端口带宽而非计算。

Cache 层次与 TLB 结构

Davinci 采用经典的哈佛结构 L1（指令/数据分离）+ 统一 L2 的三级 cache 设计，并配有两级 TLB 层次。

  • L1-I Cache：64 KB 4-way，2 周期延迟，服务前端取指。4 MSHR 支持有限的 cache miss 处理。
  • L1-D Cache：64 KB 4-way，4 周期延迟，服务标量 Load/Store。1R+1W 双端口，8 MSHR。
  • L2 Unified Cache：512 KB 8-way，12 周期延迟，16 MSHR。L1-I 和 L1-D 的 miss 均汇入 L2。MTE 的 Tile 搬运也通过 L2，但绕过 L1-D，减少中间层级。
  • TLB：I-TLB 和 D-TLB 各 64 entries 全相联，支持 4KB 和 2MB 页面。L2 TLB 512 entries 8-way，额外支持 1GB huge page。

Memory Tile Engine (MTE) 详解

MTE 是 Davinci 的 tile 数据搬运引擎，负责 TRegFile-4K 与外部存储（L2 Cache / 主存）之间的数据传输，同时支持 Tile 与标量 GPR 之间的数据转换。

  • 6 条流水线：TILE.LD（加载 Tile）、TILE.ST（存储 Tile）、Gather/Scatter（非连续搬运）、TILE.GET（提取单行到 GPR）、TILE.PUT（插入 GPR 到 Tile，支持 RMW）、TILE.COPY（Tile 间拷贝）。
  • 32-entry Outstanding Buffer：支持深度 MLP（Memory-Level Parallelism），最多 32 个未完成的 L2 请求同时飞行，有效隐藏 72-cycle 的 TILE.LD 延迟。
  • 直连 L2 路径：MTE 绕过 L1-D Cache，直接读写 L2。一个 Tile（4KB）需要 64 cycles（64B/cy 带宽）。TILE.LD 总延迟 = 72 cycles（含 epoch 写入开销）。
  • 端口使用：TILE.LD 占用 1 个写端口（W1-W7），TILE.ST 占用 1 个读端口（R5-R7）。TILE.GET 的结果通过 CDB 广播到标量域。

TILE.LD 延迟分解

  • Memory phase: ~64 cycles (from L2, 64 cache lines)
  • TRegFile write epoch: 8 cycles
  • Total (L2 hit): 72 cycles
  • Outstanding buffer: 32 entries

TILE.MOVE 消除 (Move Elimination)

TILE.MOVE 在 D2 重命名阶段完全处理，零延迟：

  • Tile RAT[Td] 指向与 Ts 相同的物理 tile
  • refcount(PT_src) += 1
  • 无 RS 分配、无执行、无 TCB 广播
  • PT_old 若 orphan 且 refcount==0 则释放

TILE.TRANSPOSE

通过专用 4 KB transpose buffer 实现完整读-转置-写：

  • Cycles 1–8: 从源 PT 读取 64 行 (512 B/cy) → 存入 transpose buffer
  • Cycles 9–16: 从 transpose buffer 写出 64 转置行 → 目标 PT
  • 总延迟: 16 cycles

双模式操作

Mode A: K-Parallel

Mode A: K-Parallel

每个 bank 接收不同的 K-group 的 A 和 B。Inter-bank adder tree 将 8 个部分积归约为共享累加器。

  • Output tile: 8 × 64 (M_tile=8, N_tile=64)
  • K consumed per step: K_step = 8 × K_mac (FP16: 8, FP8: 16, MXFP4: 64)
  • Inter-bank adder tree: active (8→1, +1 pipeline latency)
  • Accumulator: 2 KB (shared)

Mode B: M-Parallel (Independent Banks)

每个 bank 处理不同的 M-block（不同的 8 行 A）。所有 bank 使用相同的 B 数据。Adder tree 被绕过。

  • Output tile: 64 × 64 (8 banks × 8 rows × 64 cols)
  • K consumed per step: K_step = K_mac (FP16: 1, FP8: 2, MXFP4: 8)
  • Inter-bank adder tree: bypassed
  • Accumulator: 16 KB (8 × 2 KB independent)

MXU Bank 结构详解

outerCube MXU 的 4096 个 base 16-bit MAC 组织为 8 个 bank，每个 bank 包含 8 行 × 64 列 = 512 个 MAC 单元。通过 sub-word partitioning，FP8 格式每 MAC 产生 2 个乘积，MXFP4 格式每 MAC 产生 8 个乘积。

  • Bank 并行：8 个 bank 可以并行处理不同的数据块（Mode A 中不同 K-group，Mode B 中不同 M-block），提供天然的数据并行。
  • Staging Registers：A-Buf（4KB × 2, double buffer）暂存 A 操作数，B-Buf（16KB × 2 或 48KB × 3 pre-load）暂存 B 操作数。Ping-pong 缓冲允许计算与数据加载重叠。
  • Inter-bank Adder Tree：Mode A 中激活，将 8 个 bank 的部分积归约到共享累加器（8→1, +1 cycle）。Mode B 中绕过，每个 bank 独立累加。
  • FP32 Accumulator：所有格式的乘积统一以 FP32 精度累加。Mode A 使用 2KB 共享累加器（ping-pong z0/z1），Mode B 使用 16KB 独立累加器（8 bank × 2KB）。

Mode A 与 Mode B 数据流对比

outerCube 的双模式设计针对不同矩阵维度优化。两种模式共享相同的硬件（8 banks × 512 MACs），但数据流和累加方式不同。

  • Mode A (K-Parallel)：所有 bank 协作处理同一个 8×64 输出 tile。每个 bank 负责不同的 K-group，通过 inter-bank adder tree 将 8 个部分积归约。适用于 K 大（≥64）的场景，如 Transformer decode 和深层 CNN。
  • Mode B (M-Parallel)：每个 bank 独立处理不同的 M-block，产生 8 个独立的 8×64 输出 tile（拼接为 64×64）。Adder tree 被绕过，每个 bank 使用独立的 2KB 累加器。适用于 M 大（≥64）且 K 较小的场景，如 CNN 早期层。
  • 关键权衡：Mode A 的 M=4/8 利用率仅 50%（8×64 bank 中仅使用部分行）；Mode B 消除了 K-step ceiling 浪费但需要更大的累加器（16KB vs 2KB）。

outerCube 19 级流水线详解

outerCube 的 19 级流水线分为三个宏阶段，端到端延迟为 8 + 1 + 1 + 1 + 8 = 19 cycles。

  • Operand Fetch (OF0–OF7, 8 cycles)：通过 8 个读端口从 TRegFile-4K 的 8 个 bank-group 依次读取 A 操作数（R0）和 B 操作数（R1-R4），存入 Staging Registers。每 cycle 读取 512B（1 个 bank-group），8 cycles 后 4KB Tile 数据全部就位。A-Buf（4KB×2 double buffer）和 B-Buf（16KB×2 double buffer）提供 ping-pong 缓冲。
  • Compute (MUL→RED→ACC, 3 cycles)：MUL 阶段执行 4096 个并行 MAC（sub-word partitioning 支持 1:2:8 缩放）；RED 阶段通过 inter-bank adder tree 将 8 个部分积归约（Mode A 激活，Mode B 绕过）；ACC 阶段将结果 FP32 累加到 ping-pong 累加器（z0/z1）。
  • Accumulator Drain (AD0–AD7, 8 cycles)：将累加器结果通过写端口 W0 逐 cycle 写回 TRegFile-4K 的 8 个 bank-group。写回同样遵循 epoch calendar 轮转。

架构评价

对 Davinci 核心的六项关键设计决策进行评估，分析各自的优缺点与适用场景。

4.1 无 ROB 设计 Score: 8/10

优势

  • 更低的功耗和面积（无需 ROB CAM 比较逻辑）
  • 更简单的设计，减少验证复杂度
  • Ref-count 释放比 ROB retire 更快（写回即释放，无需等顺序退休）
  • 等价于 Tomasulo 原始算法 (IBM 360/91, 1967)
  • Tile RAT ready bit 替代 scoreboarding，消除 WAW/WAR

劣势

  • 不支持精确中断/异常，无法运行通用操作系统
  • 调试困难（无精确状态回溯）
  • 3-bit tile refcount（最大 7 个读者），限制了物理 tile 的共享范围
  • 仅适用于 run-to-completion kernel 场景
  • Flush 时需恢复双 RAT checkpoint + 双 free-list head

4.2 统一 Tile 寄存器 (TRegFile-4K) Score: 7/10

优势

  • 消除 VRF/CRF 之间的数据移动
  • 1 MB 软件 scratchpad，支持深度 double-buffering
  • Tile RAT 消除 WAW/WAR hazard
  • Vector、Cube、MTE 共享统一寄存器，简化数据流
  • 8R+8W 端口提供高聚合带宽 (4KB/cy read + 4KB/cy write)

劣势

  • ~1.2 mm² 面积，占核心 37%（64 banks × 256×512b SRAM）
  • 8R+8W epoch 调度复杂（8-cycle calendar rotation）
  • Cube active 时端口竞争（MXFP4 占用 5R + 1W）
  • Epoch-locked 端口：一旦 latch，8 cycles 不可变
  • 224-entry tile free list 管理 overhead

4.3 外积累积 (outerCube) Score: 8/10

优势

  • 自然的 weight-stationary 数据复用（B operand reuse）
  • B double-buffer 40KB staging + ping-pong accumulator 零停顿
  • Dual-mode 灵活性（Mode A K-parallel / Mode B M-parallel）
  • Sub-word partitioning 1:2:8 实现软件可控精度/性能权衡
  • 统一的 32-bit FP32 累加器，所有格式精度一致
  • 12.3 TFLOPS FP16, 98.3 TOPS MXFP4 @ 1.5 GHz

劣势

  • Mode A M=4/8 利用率仅 50%（K-step alignment 浪费）
  • K-step 对齐约束（非对齐 K 导致 ceiling 浪费）
  • Inter-bank adder tree +1 cycle pipeline 延迟 (Mode A)
  • Mode B 无 B broadcast MUX（每 bank 独立读 B，4 端口足够）
  • 4096 base MACs 面积 ~0.8 mm²（加 adder trees）

4.4 4 宽前端 + 单线程统一指令流 Score: 7/10

优势

  • 简化编译器/编程模型（单线程，统一地址空间）
  • 跨域 ILP（scalar + vector + cube + MTE 并行执行）
  • 统一 tile 管理（T0–T31 跨所有域共享）
  • 更小的前端面积和功耗
  • 4-wide decode + rename 足以覆盖 AI kernel 的标量开销

劣势

  • 4-wide 比 8-wide 竞争对手更窄，标量吞吐受限
  • 单线程吞吐天花板（无 SMT/多线程）
  • Cube RS 仅 4 entries（极长延迟指令缓冲有限）
  • 前端阻塞时所有域同时受影响（RS full / free list empty）
  • 标量 IPC 典型值 2.5-3.0（受分支和 cache miss 影响）

4.5 多格式低精度 (MXFP4/HiFP4) Score: 7/10

优势

  • 98.3 TOPS (8× FP16)，极致吞吐
  • 软件可控精度/性能权衡（CUBE.CFG 切换格式）
  • 统一 FP32 累加器保证累加精度
  • Sub-word partitioning 复用同一硬件（无额外乘法器面积）
  • HiFP4 提供更高 mantissa 精度选项

劣势

  • 极低精度对模型质量的影响尚不明确
  • MXFP4/HiFP4 生态系统不成熟（工具链、量化方法）
  • 量化感知训练工具链有限
  • FP4 mode adder tree 更宽（8-input, 20 bits），增加延迟和功耗
  • MXFP4 需要 4 B ports（FP16 只需 2），Cube active 时 Vector/MTE 端口减半

4.6 MTE 直连 L2 的 tile 数据通路 Score: 8/10

优势

  • 绕过 L1-D 减少 tile 数据移动层级
  • 32-entry outstanding buffer 支持深度 MLP（deep MLP layer）
  • 与 scalar LSU 独立，不竞争 L1-D 带宽
  • 64 B/cy 持续带宽，1 tile = 64 cycles from L2
  • TRegFile-4K (1MB) 作为软件管理 scratchpad

劣势

  • 分离的 scalar/tile 路径增加编程复杂度
  • TILE.LD 72cy (L2) 需要仔细的 double-buffering
  • Store buffer OoO commit 可能引起内存排序问题
  • TILE.LD/ST 默认无序，需要 FENCE 指令同步
  • MTE 指令延迟高（72 cy L2 hit, 200-400 cy DRAM）

综合评价：Davinci 核心通过无 ROB 设计和统一 tile 寄存器实现了简洁高效的 OoO 执行引擎。 outerCube MXU 的 dual-mode 外积累积提供了卓越的矩阵计算吞吐。4 宽前端虽然吞吐受限， 但在 AI 推理场景中，标量操作仅占 ~15%，主要瓶颈在 Cube 和 MTE 带宽。 整体设计在面积效率、功耗和 AI 工作负载性能之间取得了良好平衡。
